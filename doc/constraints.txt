Claude Code sandbox constraints
================================

This file documents the intent behind each constraint in
project-config/settings.json and the global configuration written to
~/.claude/settings.json by install-husk.sh.

Settings are split by scope:
  ~/.claude/settings.json — machine-wide; applies to every project regardless
    of whether the project config template was copied; written by the install
    script from user-config/settings.json.
  .claude/settings.json  — project-level template; copy from
    project-config/settings.json; covers workflow decisions that vary per
    project (network egress, MCP).

Each control below is annotated with the threat-model harm IDs it defends
against. The harm catalog (H1, H2, …, H9-out) is defined in
doc/threat-model.txt. Status notes — where defenses are partial,
compensating, or depend on user attention — are captured per-control here.


── ~/.claude/settings.json (written by install-husk.sh) ───────────────

Written to the user-global config so it applies to all projects without
per-repo setup. The install script preserves existing keys outside the
"enableAllProjectMcpServers", "sandbox", and "permissions" blocks.

enableAllProjectMcpServers: false
  Defends: H6 (exfiltration via MCP server), H8 (identity abuse via MCP).

  Prevents project-local .mcp.json files from silently activating MCP servers
  when a project is cloned. Set globally so it applies even if the user never
  copies the project config template.

sandbox.enabled: true
  Defends: meta — without this, none of the H1, H2, H5', H6, H7, H8
  defenses are active.

  Activates the bwrap + seccomp sandbox for all Claude Code sessions.

sandbox.autoAllowBashIfSandboxed: true
  Bash commands inside the sandbox run without per-command prompts. The
  sandbox itself is the guard — prompting inside it adds friction with no
  additional safety value.

sandbox.allowUnsandboxedCommands: false
  Defends: meta — prevents the agent from requesting an escape from the
  sandbox at all. Without it an inattentive user could approve unsandboxed
  execution, voiding every other defense.

  Hard-blocks all commands that would run outside the sandbox. The primary
  use case is long-running autonomous sessions (e.g. multi-day hyperparameter
  optimization) where no human is watching to approve prompts. In that context
  an unsandboxed command request is never legitimate and should just be denied.
  If you find this too restrictive in interactive sessions, set to true — but
  be aware that a sandbox users work around is no sandbox at all.

sandbox.seccomp.applyPath
  Defends: H1 (inner BPF filter layer beyond seccomp-wrapper), H6 (blocks
  AF_UNIX sockets that could otherwise be used as covert egress paths).

  Path to Anthropic's apply-seccomp binary (~/.local/lib/husk/).
  Omitted from the config if apply-seccomp was not installed (unsupported
  architecture) rather than writing a broken path.

sandbox.filesystem.denyRead / allowRead
  Defends: H2 (bash path), H7 (bash path), H8 (bash path), H9-in (when
  input data paths are added to allowRead — every allowRead entry becomes
  a bwrap --ro-bind). The native-tool path for H2, H7, H8 is defended
  separately by permissions.deny patterns; see the bash-vs-native-tools
  section below.

  denyRead: ["/users"] blocks all home directories on CSCS (where home
  directories live under /users/). This prevents the agent from reading the
  current user's ~/.ssh, API tokens, and other users' world-readable files on
  the shared filesystem. Adjust to /home (or the relevant parent) on other
  HPC systems.
  allowRead: ["./"] re-allows the current project directory.

  allowRead paths are passed to bwrap as --ro-bind arguments (confirmed via
  sandbox-runtime source). Paths outside any denyRead region are already
  accessible via the initial root bind mount — allowRead is only needed to
  punch holes back through a denyRead region. Concretely: data on /scratch/
  or other paths outside ~ is readable inside bwrap without any allowRead
  entry; only paths inside ~ need explicit allowRead to be re-exposed.

  IMPORTANT — the sandbox behaves very differently for bash vs. native tools.
  This is unintuitive and worth understanding carefully.

  Bash tool (runs inside bwrap):
    bwrap wraps each bash subprocess in an isolated mount namespace.
    ~ is visible but mounted read-only — bash can read files in ~ but cannot
    write to them (confirmed: echo > ~/.claude/settings.json returns EROFS).
    Bash cannot write outside the project directory at all.
    bwrap also replaces .claude/* with /dev/null null devices inside the
    namespace — bash sees them as character devices and cannot overwrite them.
    autoAllowBashIfSandboxed: true applies ONLY to bash — these commands run
    without per-command prompts inside the sandbox.

  Native file tools — Read, Edit, Write (run in the Claude Code process):
    These run OUTSIDE bwrap entirely and bypass its filesystem restrictions.
    denyRead: ["/users"] and allowRead: ["./"] cause Claude Code to PROMPT the
    user before proceeding, but do not hard-block access.
    autoAllowBashIfSandboxed does NOT apply — native tools always prompt,
    even inside the project directory.
    If the user approves, the tool succeeds. Confirmed:
      - Write to .claude/settings.json succeeds when approved (→ deny rules)
      - Write to arbitrary paths outside ~/ silently fails (bwrap discards)

  Summary table (confirmed by testing):
    Location              Bash              Native tools
    Project dir (./)      writable, auto    writable, always prompts
    ~/.claude/            read-only (EROFS) writable, prompts (→ deny rules)
    .claude/settings.json /dev/null, EPERM  hard-blocked by deny rules
    Elsewhere in ~/       read-only (EROFS) writable, prompts
    Outside ~/            readable, auto    writable, always prompts

  MITIGATED:
    ~/.claude/settings.json: deny rules in user-config/settings.json (written
      globally by the install script) hard-block Write/Edit regardless of
      sandbox state — the agent cannot ask the user to approve, so there is
      no approval prompt to social-engineer.
    .claude/settings.json: same deny rules block Write/Edit globally. Bash is
      blocked by bwrap's null-device mount. Together these close the
      sandbox-disable vector.

permissions.allow — SLURM read-only commands
  sinfo, squeue, sacct, scontrol show *, sprio, sreport are pre-allowed so they
  run without a permission prompt.

  IMPORTANT — these do NOT work inside the sandbox. Like every SLURM client they
  authenticate to slurmctld/slurmdbd via MUNGE and reach it over the network,
  both of which the sandbox blocks (apply-seccomp denies the AF_UNIX socket
  MUNGE needs; bwrap --unshare-net removes the route to the controller). So
  inside the sandbox these commands fail exactly like the write commands; the
  allow rules only suppress the prompt, they do not make the commands function.
  They work in the user's own (unsandboxed) shell.

  The rules are kept deliberately: they are harmless (a failed allowed command
  just returns an error the agent observes) and forward-compatible with v0.3,
  where fine-grained socket scoping is planned to let SLURM clients run
  in-sandbox. Set globally.

SLURM write commands — NOT in permissions.allow
  Defends: H3. Status: user confirmation is the only control between the
  agent and a five-figure SLURM bill. No graceful middle (budget, rate
  limit) — agent-layer policy is the expected solution; see context.txt
  under "Documented gaps and their disposition".

  sbatch, srun, salloc, scancel, and scontrol update/hold/release/requeue
  are intentionally absent from the allow list. Claude Code will prompt for
  confirmation before running them. Job submissions consume allocation and
  affect the queue for other users; cancellations and modifications affect
  running jobs. You want to stay in the loop.
  If you find yourself approving job submissions constantly, add them to allow:
    "Bash(sbatch *)", "Bash(srun *)", "Bash(salloc *)"

  v0.2.x (planned): a SLURM GATEWAY closes the deeper problem prompt-or-allow
  does not — that a submitted job runs UNSANDBOXED on a compute node (the
  SLURM-path escape). The agent never runs the real sbatch: a stub shadows it
  inside the sandbox and forwards a structured request to a broker OUTSIDE the
  sandbox, which validates it, forces safe options, and submits a job that runs
  re-sandboxed (seccomp-wrapper + bwrap) on the compute side. Built within
  v0.2.x, not gated on v0.3. Note SLURM does not work from inside the sandbox
  at all today (MUNGE/AF_UNIX + --unshare-net — see "permissions.allow SLURM
  read-only commands" above). Full design in context.txt "SLURM-path escape".

permissions.deny — credential files
  Defends: H2 (native-tool path, plus the file-reading bash commands Claude
  Code recognizes — cat/head/tail/sed). Status: covers well-known credential
  patterns. Unusual locations (~/.netrc, ~/.kube/config, ~/.config/gh,
  tokens stored at non-standard paths) are NOT covered and depend on the user
  noticing prompts. The bash path for H2 is defended by bwrap denyRead. An
  arbitrary subprocess (e.g. a python script that opens the file itself) is
  NOT caught by these rules — only the OS bwrap layer catches that.

  Pattern syntax + the Config-tab warning (Linux). Read/Edit/Write rules follow
  gitignore semantics with the anchors at code.claude.com/docs/en/permissions:
    //path  absolute from filesystem root     ~/path  home-relative
    /path   project-root-relative             path    cwd-relative, any depth
  We use the "//**/" form (filesystem-wide) so credential files are denied
  anywhere, not just under the project directory.

  The /sandbox Config tab warns "glob patterns not fully supported on Linux —
  the following will be ignored" for ANY glob deny rule (a leading "**/", the
  "//**/" anchor, or even a single "*"). This warning is about the bwrap SANDBOX
  BOUNDARY ONLY: bwrap denies by bind-mounting specific paths and cannot express
  a glob, so glob deny rules can't be baked into the OS boundary. It does NOT
  mean the rules are unenforced. They are enforced by the PERMISSION LAYER —
  Claude Code's gitignore matcher applied to the native Read/Edit/Write tools
  and to recognized bash file commands (cat/head/tail/sed), which is
  platform-independent. Confirmed on Santis 2026-06-04: a native Read of a .env
  was DENIED by the permission layer, and `cat .env` in the cwd was blocked at
  the OS layer by the mandatory-deny scan's /dev/null mount — both paths
  protected. The warning is cosmetic for our purpose. (Only exact-path rules,
  like the settings.json ones below, avoid it, because bwrap can mount over a
  concrete path.)

  //**/.env*  (Read/Edit/Write): hidden env files anywhere (.env, .envrc,
    .env.local, .env.production, …).
  //**/*.env  (Read/Edit/Write): non-hidden env files (production.env, …).
  //**/*.pem, //**/*.key (Read/Edit/Write): PEM certs and private keys.
  //**/credentials (Read/Edit/Write): the `credentials` convention (e.g.
    ~/.aws/credentials).
  The "//**/" anchor is filesystem-wide and deliberately stronger than the
  old cwd-anchored form: it now also covers home-dir credentials on the
  native-tool path, matching bwrap's /users denyRead on the bash path.
  Caveat: deny beats allow, so a filesystem-wide //**/*.key cannot be
  re-allowed for one legitimate file — narrow the pattern if a workflow needs
  a specific key. The agent has no reason to touch credential material; if it
  needs an env var it should be passed explicitly. Set globally.

  v0.3 note: these permission-layer rules exist ONLY because Claude Code's
  Read/Edit/Write tools run in-process, outside bwrap (the native-tool
  asymmetry). Under the v0.3 sandbox-interface contract all such tools run as
  subprocesses, so the OS filesystem boundary covers them uniformly and these
  rules become redundant — the credential-name intent migrates into bwrap
  denyRead. See doc/sandbox-interface.txt.

permissions.deny — nc / socat
  Defends: H6. Status: compensating control — blocks two common bash-tool
  exfiltration paths. The architectural defense for H6 is the
  --unshare-net + socat proxy plus an allowlist; these rules close known
  gaps until allowlist policy is configured.

  nc (netcat):
    A direct exfiltration tool with no legitimate use in a coding agent
    workflow. Hard deny globally.

  socat:
    A capable TCP relay that would otherwise bypass the nc block. Same
    reasoning — hard deny globally. Note: socat is also installed by the
    install script as a runtime dep for bwrap, so it will be on PATH.

permissions.deny — settings.json (sandbox-config integrity)
  Defends: meta — preserves all other defenses by preventing the agent
  from disabling the sandbox or removing any deny rule between sessions.

  Edit/Write on three targets (the leading-**/ glob was dropped on Linux;
  fixed 2026-06-01 to anchored forms — see the credential-files note above):
    ~/.claude/settings.json       the machine-wide config, where the sandbox
                                  is actually enabled. The OLD
                                  **/.claude/settings.json never matched this
                                  (it was cwd-anchored), so the home config was
                                  unprotected on the native-tool path even
                                  before the Linux drop. Now covered explicitly.
    .claude/settings.json         the project-level config.
    .claude/settings.local.json   project LOCAL settings. Critical: local
                                  project settings OUTRANK user settings in
                                  Claude Code's precedence, so an agent that
                                  writes this file with "sandbox":{"enabled":
                                  false} disables the sandbox next session.
                                  The old config did not deny this file at all.
  An agent that rewrites any of these escapes the sandbox on the next session.
  Hard blocks — the agent cannot ask the user to approve, so there is no
  prompt to social-engineer.

  These deny rules ARE necessary despite bwrap's null-device protection:
    Inside bwrap, Claude Code replaces .claude/* with /dev/null, so bash
    cannot write them (echo > .claude/settings.json returns EPERM). But the
    native Write tool runs OUTSIDE bwrap and CAN create these as real files on
    the underlying filesystem (confirmed). The deny rules block the
    Write/Edit tools entirely, closing the native vector; bwrap closes bash.

  Stronger hardening (recommended, needs admin): put "sandbox":{"enabled":
  true} in /etc/claude-code/managed-settings.json. Managed settings cannot be
  overridden by user/project/local settings, so the sandbox cannot be turned
  off by editing any user-writable file — closing the override vector
  structurally instead of by enumerating files to deny. A CSCS-admin ask;
  pair it with the admin-side SLURM layer.


── project-config/settings.json ─────────────────────────────────────────────

This file is a template. Copy it to .claude/settings.json in your project and
commit it so restrictions apply to everyone working on the project. It covers
only the workflow decisions that vary per project.

permissions.deny — network egress
  ssh / scp / rsync:
    Defends: H5 (SSH to compute nodes). Bash-tool deny is the active
    control; bwrap does not block ssh-as-a-binary, only network reachability.

    The agent should not be able to exfiltrate data or reach other cluster
    nodes directly. On CSCS supercomputers, SSH to compute nodes from a login
    node is common for humans but should require explicit confirmation for an
    agent.
    DECISION NEEDED: remove from deny if you regularly ask Claude to run
    commands on compute nodes — it will then prompt for confirmation.

  curl / wget:
    Defends: H6 (compensating control until network.allowedDomains policy
    is configured — see Network isolation section below).

    Outbound HTTP/HTTPS. The agent legitimately needs these to fetch
    documentation or download files, but unrestricted outbound access from a
    shared login node is a risk (data exfiltration, reaching internal cluster
    services).
    DECISION NEEDED: remove from deny if your project requires fetching data.

    ALTERNATIVE: Claude Code's sandbox supports a network.allowedDomains
    allowlist enforced at the proxy level (add a "network" block to
    user-config/settings.json). This is stronger than tool-level deny rules
    since it applies to all outbound traffic, not just explicit curl/wget
    invocations. Domain policy is an open decision for this project.

  mcp__*:
    Defends: H6 (exfiltration via MCP server), H8 (identity abuse via MCP
    credentials).

    Blocks all MCP tool calls. A compromised or malicious MCP server could
    otherwise be used as a pivot point. Disable unless you are deliberately
    using specific MCP servers you trust.
    Note: enableAllProjectMcpServers: false (set globally) blocks project-local
    .mcp.json files from auto-loading servers, but user-level MCP servers in
    ~/.claude/ are unaffected — review those independently.


── SECCOMP_WRAPPER_DEBUG ─────────────────────────────────────────────────────

SECCOMP_WRAPPER_DEBUG=1 is a development-only escape hatch documented in
husk/README.md. It swaps SCMP_ACT_KILL_PROCESS for SCMP_ACT_ERRNO(ENOSYS)
so blocked syscalls return an error instead of killing the process. Never set
this in a production session — it disables enforcement for the duration of the
run. The AI agent is the threat model here; human users can legitimately set
this variable for profiling and testing.


── sandbox dependency stack ──────────────────────────────────────────────────

bubblewrap (bwrap):
  Provided system-wide on CSCS supercomputers; should be available on any HPC
  system where administrators have installed it. Runs each agent subprocess in
  an isolated filesystem namespace with only the current project directory
  bind-mounted in.

apply-seccomp (~/.local/lib/husk/apply-seccomp):
  Static binary from @anthropic-ai/sandbox-runtime, extracted by the install
  script. Wraps each agent subprocess in a nested user+PID+mount namespace
  (agent cannot see or ptrace the outer process tree) and applies a BPF filter
  blocking socket(AF_UNIX,...) and io_uring. Uses SCMP_ACT_ERRNO — blocked
  calls return EPERM, the agent can observe and report the error.

seccomp-wrapper (~/.local/bin/seccomp-wrapper):
  Static binary from husk/, compiled on the target machine with
  gcc -static. Installs a broad syscall deny-list (ptrace, kexec_load, bpf,
  pivot_root, etc.) using SCMP_ACT_KILL_PROCESS before exec'ing claude.
  Stacks on top of apply-seccomp — the kernel applies both filters,
  most-restrictive wins. When a blocked syscall is attempted the offending
  subprocess is killed; Claude sees the exit code, reasons about it, and
  continues the session.

husk (~/.local/bin/husk):
  Thin launcher script: exec seccomp-wrapper claude "$@"
  Users invoke husk instead of claude.


── Network isolation ─────────────────────────────────────────────────────────

Defends: H5' (solved by --unshare-net architecture), H6 (architecturally
solved by --unshare-net + proxy; the active policy lives in
sandbox.network.allowedDomains / sandbox.network.deniedDomains).

The network isolation infrastructure is in the sandbox-runtime: bwrap runs
with --unshare-net, removing the network namespace entirely. All outbound
traffic from inside the sandbox must go through host-side socat proxy
sockets (HTTP port 3128, SOCKS5 port 1080) that are bind-mounted into the
bwrap namespace — no other network path exists.

network.allowedDomains / network.deniedDomains:
  Enforced at the proxy level — applies to all outbound traffic regardless
  of which tool makes the request, which is stronger than tool-level deny
  rules. Configured in user-config/settings.json for machine-wide policy
  or .claude/settings.json for per-project policy. Example:

    "sandbox": {
      "network": {
        "allowedDomains": ["api.anthropic.com", "pypi.org", "github.com"]
      }
    }

  The agent cannot modify these settings — settings.json is hard-blocked
  by the existing Edit(**/.claude/settings.json) deny rules. The user
  maintains the file directly. The proxy picks up changes without
  restart.

Two postures, picked per project:

  strict — default deny outside the allowlist. Best for production data
    pipelines, unattended runs, and projects with a known fixed set of
    endpoints. The user lists the domains the project actually needs.
    When using strict, remove curl/wget from the project's
    permissions.deny — the proxy is now the active control and applies
    to all outbound traffic, not just explicit curl/wget.

  permissive — default allow except a known-bad blocklist. Best for
    general coding assistance and research where the agent reads
    documentation from unpredictable domains. Accepts looser H6
    protection in exchange for not fighting the workflow. Keep curl/wget
    in the project's permissions.deny as a compensating control.

When the proxy blocks a request, the agent sees an HTTP 403 with a
structured error. The agent can surface this to the user ("I tried to
access X; not on the allowlist") but cannot expand the allowlist
itself. The user must edit the settings file to permit a new domain.
This is deliberate: an agent that could expand its own permissions
would bypass the H6 control entirely.


── Audit trail ──────────────────────────────────────────────────────────────

Claude Code writes a per-session JSONL transcript to
~/.claude/projects/<encoded-project-path>/<session-id>.jsonl containing every
user prompt, every tool call (Read / Edit / Write / Bash) with arguments,
every tool result, and every model response. This is the audit log available
for forensic incident review without admin cooperation.

Covers:
  - H2, H4, H7, H8 — every native-tool call with arguments
  - H3 — every sbatch / srun / scancel invocation
  - Agent intent — model responses captured verbatim

Does not cover:
  - Subprocess-level activity. If the agent runs `python script.py`, the
    transcript captures the bash invocation and stdout/stderr but not what
    the spawned process opened, wrote, or sent.
  - Network at the wire level. The socat proxy bridges by default; it does
    not log requests. Projects with high H6 exposure can enable socat
    logging as an opt-in — see context.txt under "Documented gaps and
    their disposition".
  - Real-time alerting. Review is forensic only.

Sensitivity:
  The transcripts contain verbatim user prompts plus any content pasted
  into them. Over time this becomes a comprehensive behavioral record —
  writing style usable as a stylometric biometric, research direction,
  occasionally secrets the user did not realize they were pasting (token
  in an error message). Treat the transcript directory as sensitive
  personal data: do not share whole transcripts casually, prune ones you no
  longer need. The install script displays a notice about this at install
  time.


── Operational mitigations for uncovered harms ──────────────────────────────

Some harms do not have an in-sandbox control. The sandbox handles what it
can; the rest depends on operational discipline from the user or policy
from the agent. Cross-reference: see "Documented gaps and their
disposition" in context.txt for the disposition framing.

H4 (project-directory data destruction)
  The project directory is the agent's writable working surface; the
  sandbox does not prevent the agent from writing to or deleting files
  there. Recommended pattern:

    - Keep precious data outside the project directory. Read-only access
      from inside the sandbox is automatic for any path outside /users
      (via the root bind mount).
    - For paths inside /users (e.g. ~/data, ~/datasets), add them to
      allowRead. Every allowRead entry becomes a bwrap --ro-bind, so the
      agent can read but not modify.
    - Take backups of the project directory before any long-running or
      autonomous session. The sandbox does not preserve a snapshot.
    - For shared scientific datasets that must remain unchanged, mount
      them at a path outside the project directory and reference them
      read-only.

H3 (compute resource abuse)
  See "SLURM write commands — NOT in permissions.allow" earlier in this
  file. The prompt-per-submission pattern is the v0.2 disposition; an
  agent-layer budget / rate-limit policy is the expected v0.3 path. v0.2
  has no built-in budget mechanism.
