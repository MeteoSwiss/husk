## POSITIVE FINDINGS (demonstrated)

1. **Silent truncation at MAX_FORWARDED_ENV=512** (jobs 5007228/5007231/5007237). Forwarding
   >512 env entries truncates to 512 with NO warning and srun exit 0 (order-deterministic:
   alphabetically-first 512 of the added delta survive). Matches the brief's named finding
   ("silent truncation would be the finding"). IMPACT IS BOUNDED on this platform: only the
   agent's OWN excess added (--setenv) vars are dropped; husk's credential/internal masks,
   control vars (HUSK_NET_SOCK/HUSK_SOCAT), proxy config, and PATH/HOME are applied outside the
   truncated set and SURVIVE; the rank base is minimal so no job-removed var was left set. The
   residual risk (a dropped --setenv silently changing rank behavior, e.g. a job that relies on
   forwarding a specific var past position 512) is real but not an isolation escape. Recommend
   husk WARN or fail-closed at the bound instead of truncating silently.

2. **Ordering (#2): the forwarded delta's --setenv beats the mask's --unsetenv for any name husk
   does not explicitly protect** (job 5007225). Demonstrated for GPU-visibility vars
   (CUDA_VISIBLE_DEVICES, ROCR_VISIBLE_DEVICES, ZE_AFFINITY_MASK, GPU_DEVICE_ORDINAL): a value
   the agent puts in the job env is restored in the rank after the mask removed it. NOT an escape
   (these are not secrets; GPU access is cgroup-enforced), but it confirms the mechanism the
   brief flagged is live. A genuine credential would be restorable this way IFF husk's
   "configured credentials" filter misses it — see reproducer R1.
