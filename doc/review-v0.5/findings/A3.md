FINDING 1 (feature-failing / "legitimate run script refused") — husk's #SBATCH
scanner is over-broad: it matches `^\s*#SBATCH` on ANY line of the body, not just
the contiguous leading comment block, and it accepts leading whitespace.
===============================================================================
Evidence (all responses are husk's, at submit time):
  - `#SBATCH --partition=short` placed AFTER a command line  -> SUBMITTED (job 5007509)
  - same directive INSIDE a `cat <<EOF … EOF` heredoc body   -> SUBMITTED (job 5007510)
  - same directive INDENTED with leading spaces `   #SBATCH`  -> SUBMITTED (job 5007512)
  - same directive inside single/double quotes (`echo "…"`)   -> not seen (line starts with echo)
  - real leading directive (control)                          -> SUBMITTED (5007508, 5007511)
Real `sbatch` scans only the leading comment block, requires column-0 `#SBATCH`, and stops at
the first command. husk scans the whole file and allows indentation → strictly broader.

Impact — confirmed false-reject of a VALID job (no job submitted; witness is the reject):
  A body whose ONLY real directives are `#SBATCH --partition=short` + minimal resources, which
  then writes a NESTED sbatch script via a quoted heredoc:
      cat > inner.sbatch <<'EOF'
      #!/bin/bash
      #SBATCH --qos=debug
      #SBATCH --reservation=maintenance
      echo inner job
      EOF
  → husk REJECTS the OUTER job:
      "#SBATCH --qos: husk does not let a job choose its QOS … Submit without --qos."
  There is no --qos on the actual job — those bytes are heredoc DATA that never reach any
  scheduler (body doesn't reach slurmd; confirmed separately). Generating inner batch scripts via
  heredoc is a common HPC/workflow pattern (job-generating-jobs, parameter sweeps, ICON/COSMO run
  scripts). Any body containing a `#SBATCH --qos/--reservation/#BB/#DW/<unknown>` line as data —
  in a heredoc, after a command, or indented — is refused. This is the brief's "legitimate run
  script refused" finding. Not an escape (husk errs toward rejecting), but it breaks valid work
  and its over-broad scan is a semantic divergence from sbatch.
  Reproducer id used: husk-review-falsereject (spec in run log).

FINDING 1 — addendum (scanner fully characterized)
===============================================================================
Scanner behaves as ~ `^[ \t]*#SBATCH\b` (and `^[ \t]*#(BB|DW)\b`) matched on EVERY line of the
whole body, last-match-wins for repeated options:
  - CRLF line endings: CR stripped, directive recognized -> legit Windows-edited script SUBMITS
    (job 5007513). (Good: no false-reject here.)
  - BOM before `#SBATCH`: NOT recognized -> "no partition" reject (minor false-reject; BOM in a
    shell script is degenerate anyway).
  - `#BB` inside a heredoc body -> rejected ("burst-buffer/DataWarp … not permitted"). So the
    over-broad match also covers #BB/#DW, which don't even need the #SBATCH prefix.
  - indented `   #SBATCH --qos=debug` -> rejected (qos). Confirms leading-whitespace acceptance.
  - PRECEDENCE last-wins: leading valid `#SBATCH --partition=short` + a later phantom
    `#SBATCH --partition=husk-review-invalid` -> REJECTED. A trailing phantom line (e.g. one
    inside a heredoc that writes an inner script with a different partition) OVERRIDES the real
    leading directive. So the over-broad scan can also flip husk's *emission* decision from
    runtime data, not just cause forbidden-directive rejects.
Net: husk's directive scan is strictly broader than sbatch (whole-file, indented, #BB/#DW,
last-wins). It never lets the agent EMIT something new (all emitted options remain confined /
allowlisted / inherited), so this is not an escape — it is a correctness/usability defect that
REFUSES legitimate bodies (and can mis-pick a value from body data). Fix direction: scan only the
contiguous leading comment block, require column-0 `#SBATCH`, stop at the first non-comment line
— i.e. match sbatch's own directive-scan semantics.
