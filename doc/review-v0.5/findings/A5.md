## 1. Boundary walk — hop 0 (in-cage stub) → hop 1 (login broker): field re-validation

Method: I bypass the dumb stub and write `req-*.json` directly into the spool with adversary-chosen
fields, then read the broker's `resp`/side effects. This is the real assumed-breach surface
(the stub makes no trust decisions; brief starting point #3). All probes below are read-only
`squeue` or rejected `sbatch` — **no compute job was launched**.

Fact confirmed first: the broker reads the `id` from the **JSON body**, not from the request
filename. (Probe 3: filename `req-fname-<uuid>.json` + JSON `id` containing a slash → broker
used the JSON id and produced no deliverable resp.) So every field in the JSON is what the
broker acts on.

### 1a. `req.id` — the cross-hop identifier (brief ★ / starting points #3,#4) — DEFENDED (null)

`id` is an opaque correlation token to the stub (hop 0), but at the broker it becomes a path
component: `resp-<id>.json` and (per brief) `<write-root>/.husk-body-<id>.sh`, and is a deletion
target at hop 2. The laundering hypothesis: forge `id` so the trusted, UNCAGED broker writes/deletes
outside its confinement.

Result: **the broker validates `id` against a strict charset before using it as a path.**
Character battery (each char embedded in `c<CHAR>c`, sent as a squeue id, checked whether a
resp was produced):
- ACCEPTED: letters, digits, `-`, `_`  (i.e. `[A-Za-z0-9_-]`).
- REJECTED (no resp): `.` `/` and EVERY shell metachar tested — `; $ \` ' " \ | & ( ) < > * ? ! ~ = @ # % , ^ { } [ ]`, space, and newline.
- Non-UUID ids like `plainAAAA` are accepted, so it is a charset check, not a UUID check — but the charset excludes exactly the traversal (`.`,`/`) and shell-injection characters.

Consequences (all attempts, all failed = defense held):
- Path traversal via id: BLOCKED. `id=esc/../../husk-review-<tag>` (with a planted `resp-esc/`
  helper dir so the `..` could resolve) → broker wrote nothing; the canary did NOT land in A5.
  A `/`-containing id simply yields no deliverable resp.
- Shell injection via id (relevant to the hop-2 deletion of the body file): BLOCKED — `;`,`$`,
  backtick, quotes, spaces, newlines all rejected.
So the "one agent-supplied string, two hops, two operations" carrier is neutralised by an
input-charset gate at the first hop. NULL RESULT for the id vector.

### 1b. `cwd` / `--chdir` / `--output` / `--error` — writable-set confinement — DEFENDED

Probe 2: valid minimal sbatch with `cwd` = a dir OUTSIDE the writable set →

### 1c. `--partition` — allowlist — DEFENDED

## 2. The environment channel (brief starting point #2: "env carried down the chain")

The stub forwards the agent's `SBATCH_*`/`SLURM_*` env in the request; a breached agent writing
the spool directly can put ANY keys in `env`. Tested what the broker does with them (submit-time):

- `SBATCH_PARTITION=debug` with no argv `--partition` → REJECTED by the allowlist (broker reads the
  env partition AND allowlist-checks it). DEFENSE.
- `SBATCH_PARTITION=debug` WITH argv `--partition=short` → job ran on `short` (argv wins, allowlisted). DEFENSE.
- `SBATCH_RESERVATION=<bad>` and `SBATCH_ACCOUNT=<bad>` → job was **submitted to short, NOT rejected**.
  If the broker had forwarded these into the real `sbatch` process env, slurmctld would have rejected
  "invalid reservation/account" at submit. It didn't → the broker does **not** blindly pass the
  agent's `SBATCH_*` env into the real sbatch. DEFENSE-consistent.
- `SBATCH_UENV=<img>` (env form of the uenv option) → REJECTED by the uenv gate. DEFENSE.

### 2a. LEAD (UNCONFIRMED): uenv gate asymmetry on low-level `UENV_*` env vars

husk's uenv gate rejects every documented channel: `--uenv/--view/--repo` (argv), `SBATCH_UENV` (env),
and `#SBATCH --uenv/--view` (body). But it does **NOT** reject the low-level uenv-runtime env vars
`UENV_VIEW` / `UENV_MOUNT_LIST` at submit time — a request carrying
`UENV_MOUNT_LIST=/…/evil.squashfs:/ , UENV_VIEW=default` was accepted (job 5009652).
`UENV_MOUNT_LIST` is exactly the variable that names a squashfs image and its mountpoint — the F26
shape ("a value benign to the submission check that could become a mount at the slurmd layer").

**This is NOT a confirmed finding.** Whether those env vars actually propagate to and are honored by
the job (hop 2) is UNCONFIRMED, because every brokered job I submitted failed at the `.batch` step
before any body ran (see §5) — so I never observed the job environment. Counter-evidence that it may
be harmless: §2 shows the broker does not forward agent `SBATCH_*` env into the submission, so it may
strip `UENV_*` as well; and there is no uenv SPANK plugin in `/etc/slurm/plugstack.conf.d`
(only `nohome.so`), so it is unclear what would consume `UENV_MOUNT_LIST` for a brokered batch job here.

Per the rules of engagement (halt on a live/dangerous mount finding; describe don't detonate), I did
NOT attempt a real squashfs mount. **Reproducer for a human / a broker unit test:** submit a brokered
job with `env={"UENV_MOUNT_LIST":"<a real readable squashfs>:/<mnt>","UENV_VIEW":"default"}` in a
context where the batch body actually executes, and check inside the job whether `<mnt>` is mounted
from the agent-chosen image (i.e. whether `UENV_*` survived husk's env handling). If it mounts, the
uenv gate is bypassable via the low-level env vars and must be extended to strip/normalise `UENV_*`.

## 7. Confirmation of the hop-2 blocker (updates §5 / §2a)

Retested with a CLEAN empty cwd subdir (no masked dotfiles), both with and without the injected
`UENV_*` env. Both jobs failed identically and instantly at `.batch`:
`bwrap: Can't mkdir /scratch/mch/cmueller/husk-review/A5/.vscode: Not a directory` (jobs 5009731/5009732).

Conclusions:
- The job cage-build (bwrap) binds the **project root** `A5` into every job cage regardless of cwd;
  `A5` contains the OUTER husk session's `/dev/null`-masked dotfiles (`.vscode`,`.bashrc`,…) which
  are not directories, so bwrap cannot create them as mount points → the job dies before the body runs.
  This is a nested-husk / review-environment artifact, and it is FAIL-CLOSED (the job aborts rather
  than running a half-built cage). It is not itself a husk security finding.
- Because the error is IDENTICAL with and without `UENV_MOUNT_LIST`, the §2a uenv-env jobs failed for
  THIS reason, not because of the injected mount vars — so §2a remains an UNCONFIRMED submit-time lead,
  and the confirmation that `UENV_*` propagates/mounts at hop 2 must be obtained where cage-build
  succeeds (a non-nested husk, or a broker unit test).
- Net effect: hops 2→3→4 (job body, in-cage `srun` stub → step-broker → rank/bwrap incl. the MUNGE
  mask) were not observable from this position. A job did create `.husk-step-spool-<jobid>` (hop-3
  spool infra) before dying, confirming the chain's shape, but the step-broker never initialised
  (empty spool), so nothing at hop 3 could be exercised.

Orphaned-artifact note (resource-lifecycle, brief starting point #5): a job that dies at cage-build
leaves its `<write-root>/.husk-body-<id>.sh` behind (the in-cage guard that deletes it never runs).
These accumulated in `A5` across the failed submissions. Harmless here (each is the agent's own body,
`id`-charset-safe), but a triager may want the broker/guard to also clean the body file on job-setup
failure, not only on normal guard exit.
